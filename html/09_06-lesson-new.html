Урок 9.6. Куда дальше: карта роста

Аннотация:
ПривычкаБот закончен: он работает на сервере, пишет сам, переживает сбои. Но бот, которым пользуются, не бывает законченным навсегда. Пользователей становится больше, появляются просьбы, вы сами захотите новое. И каждый раз будет вопрос: что изучать дальше?

Этот урок — не учебник по восьми новым темам, а карта. Про каждую тему — три вещи: что это, по какому сигналу понять, что она вам нужна, и с чего начать. Две темы мы потрогаем руками на коде ПривычкаБота, остальные — опишем.

🧭 1. Как читать эту карту

Вспомните, как появлялись темы курса. База данных — не в начале, а когда привычки начали исчезать при перезапуске (урок 7.1). aiohttp — когда понадобилась погода, а requests остановил бы бота для всех (урок 8.1). Сервер — когда напоминание в 07:30 оказалось невозможным на спящем ноутбуке (урок 9.1).

У каждой технологии есть сигнал — момент, когда без неё больше нельзя. Учить её до сигнала можно, но знание без задачи плохо держится. После сигнала учится быстро: вы знаете, зачем.

Поэтому у каждой темы ниже одна и та же схема:

что это       →  одной-двумя фразами
сигнал        →  что случится с ботом, когда тема станет нужна
первый шаг    →  с чего начать
из курса      →  что вы уже умеете и что пригодится

Не нужно идти по карте подряд. Дочитайте до конца, запомните сигналы и возвращайтесь к теме, когда её сигнал прозвучит.

🧪 2. Тесты

Что это. Программа, которая проверяет вашу программу. Вы один раз пишете: «вызвать is_due("07:30", ...) в 07:45 — должно быть False». Дальше эту проверку выполняет компьютер, сколько угодно раз, за секунды.

Сигнал. Вы боитесь менять код: вдруг сломается то, что работало. Или приёмка из урока 9.5 после каждой правки занимает полчаса.

Попробуем

Самый распространённый инструмент для тестов на Python — pytest. Поставьте его в окружение проекта:

Создайте в проекте папку tests, а в ней файл test_logic.py:

from datetime import datetime

def test_morning_on_time():
    assert is_due("07:30", datetime(2026, 11, 2, 7, 30))

🚧 3. Middleware и защита от спама

Что это. Middleware — код, через который проходит каждое обновление до хэндлера. Он может что-то записать, что-то проверить или решить, что до хэндлера дело не дойдёт.

Сигнал. Один и тот же код в начале каждого хэндлера: проверить, не заблокирован ли пользователь, записать что-то в журнал. Или кто-то жмёт кнопки как пулемёт, и бот тратит на него всё время.

Как это выглядит

Сделаем простую защиту: не больше одного сообщения в секунду от одного пользователя. Для этого впервые в курсе придётся написать свой класс — aiogram ждёт middleware в такой форме. Создайте в проекте файл throttle.py:

import time

from aiogram import BaseMiddleware
from aiogram.types import Message


class ThrottleMiddleware(BaseMiddleware):
    def __init__(self, seconds: float = 1.0) -> None:
        self.seconds = seconds
        self.last: dict[int, float] = {}

    async def __call__(self, handler, event: Message, data: dict):
        user_id = event.from_user.id
        now = time.monotonic()
        if now - self.last.get(user_id, 0.0) < self.seconds:
            return None
        self.last[user_id] = now
        return await handler(event, data)

Как это читать, вы знаете с урока 4.1. ThrottleMiddleware наследуется от BaseMiddleware из aiogram. В __init__ заводятся пауза и словарь «пользователь → когда писал последний раз». __call__ aiogram вызывает на каждое сообщение. Внутри — знакомая логика: прошло меньше секунды — вернуть None и не звать хэндлер; иначе запомнить время и передать сообщение дальше через await handler(event, data).

Подключается одной строкой в main(), после создания dp:

dp.message.middleware(ThrottleMiddleware())

Мы проверили на стенде: Аня отправила /menu дважды с паузой 0,2 секунды, потом Борис, потом Аня ещё раз через секунду:

  Аня: /menu
  Бот: Главное меню …
  Аня: /menu
  Бот: (не отвечает)
  Борис: /menu
  Бот: Главное меню …
  Аня: /menu
  Бот: Главное меню …

Второе сообщение Ани не дошло до хэндлера. Борис не пострадал: у него свой счётчик. Через секунду Аня снова получает ответы.

Из курса. Чтение классов (4.1), словарь с user_id (7.4), time.monotonic() из опытов уроков 8.1 и 9.1.

Первый шаг. Раздел документации aiogram о middleware. Документация на английском, перевод страницы в браузере справляется. Хорошая первая задача — middleware, который пишет в журнал, сколько миллисекунд обрабатывалось каждое сообщение.

📣 4. Админка и рассылки

Что это. Команды, которые работают только для владельца бота: статистика по всем пользователям, объявление всем сразу.

Сигнал. Ботом пользуются десятки людей, и вам нужно сказать им всем, что завтра бот обновится. Или хочется знать, сколько людей отмечали привычки на этой неделе.

Что для этого нужно

  • Кто админ. Свой user_id — в .env, как токен (урок 4.2). Хэндлер админской команды проверяет message.from_user.id — по правилу урока 7.4: номер берётся только оттуда. Фильтр F из урока 4.3 умеет это одной записью.
  • Кому слать. get_user_ids() из урока 9.1 уже возвращает всех, у кого есть привычки.
  • Как слать. bot.send_message() и deliver() из урока 9.1. TelegramForbiddenError от тех, кто заблокировал бота, вы уже ловите.

Чего не хватает: лимиты

Telegram ограничивает скорость. По официальному FAQ для ботов: в один чат — не чаще сообщения в секунду, а всего при рассылке — не больше примерно 30 сообщений в секунду. Если превысить, Telegram начнёт отвечать ошибкой 429, и aiogram поднимет TelegramRetryAfter с числом секунд, которые нужно подождать.

Для ПривычкаБота с утренним сообщением на десяток человек это не важно. Для рассылки на тысячу — важно: между отправками нужна пауза, await asyncio.sleep(), а на TelegramRetryAfter — подождать сколько сказано и повторить.

Из курса. .env (4.2), F (4.3), from_user.id (7.4), рассылка с deliver() (9.1), asyncio.sleep() (модуль 3).

Первый шаг. Команда /admin_stats — число пользователей и отметок за сегодня. В ней нет рассылки, а значит, нет и лимитов.

💾 5. Диалоги, которые переживают перезапуск

Что это. Хранилище состояний FSM вне памяти процесса.

Сигнал. Пользователь создавал привычку, вы как раз обновили бота — и диалог оборвался. Мы проверили на стенде. Аня начала создание привычки:

состояние: None
  Аня: /add
  Бот: Как назовём привычку?

       [ ✖️ Отмена ]
       [состояние: AddHabit:waiting_for_name]

Бота перезапустили — systemctl restart habitbot после обновления. Аня отвечает на вопрос:

состояние: None
  Аня: Растяжка
  Бот: Я пока понимаю только команды. Загляните в /menu
       [состояние: None]

Бот не помнит, что ждал название. Об этом предупреждал урок 6.1: Dispatcher() по умолчанию хранит состояния в оперативной памяти, а она живёт, пока живёт процесс. Привычки после модуля 7 переживают перезапуск, а незаконченные диалоги — нет.

Что с этим делают

В aiogram хранилище меняется одним аргументом Dispatcher(storage=...), а хэндлеры диалога остаются как есть. Самый частый выбор — RedisStorage. Redis — отдельная программа-хранилище на сервере, очень быстрая; в ней состояния и черновики диалогов лежат вне процесса бота и переживают его перезапуск.

Для ПривычкаБота это пока не беда: диалог короткий, обновления редкие, а оборванный диалог начинается заново одной командой. Беда начинается, когда диалоги длинные, а обновления частые.

Из курса. FSM и FSMContext (модуль 6), установка программ на сервер через apt (9.2).

Первый шаг. Поставить Redis на сервер и передать RedisStorage в Dispatcher. Остальной код бота не меняется — ради этого FSM в aiogram и отделён от хранилища.

🐘 6. PostgreSQL

Что это. База данных, которая работает отдельной программой-сервером. SQLite — файл, который открывает сам бот. PostgreSQL — служба, к которой бот подключается по сети, как к Telegram.

Сигнал. С базой работает не только бот. Например, вы сделали сайт-админку, или запустили вторую программу для рассылок, и всё чаще видите database is locked из урока 9.4. SQLite пускает одного писателя за раз, PostgreSQL рассчитан на многих.

Что поменяется, а что нет

Поменяется немного: другая библиотека вместо aiosqlite, например asyncpg; другие метки для значений — $1, $2 вместо ?; адрес и пароль базы в .env; служба базы на сервере.

Не поменяется главное: SQL. SELECT, JOIN, GROUP BY, ON CONFLICT из модулей 7–9 работают в PostgreSQL так же. В CREATE TABLE поправятся типы: например, автоматический номер записывается не через AUTOINCREMENT. И не поменяются хэндлеры: все запросы живут в database.py. Переезд базы — переписывание одного файла, ровно как в уроке 7.4 бот переехал со storage.py на database.py.

Из курса. SQL (модуль 7), async with и await для соединения (7.2), значения только через метки, а не f-строкой (7.2).

Первый шаг. Поставить PostgreSQL на свой компьютер и повторить таблицы и запросы урока 7.3 в его консоли. Переводить бота — когда появится сигнал.

🪝 7. Вебхуки

Что это. Другой способ получать обновления. Сейчас бот сам постоянно спрашивает Telegram: «есть что-нибудь новое?» — это опрос, start_polling(). С вебхуком наоборот: Telegram сам присылает каждое обновление на адрес вашего сервера, как только оно появилось.

опрос:   бот  →  Telegram:  «есть новое?»   (постоянно)
вебхук:  Telegram  →  сервер бота:  «вот новое»   (когда есть)

Сигнал. Ботом пользуются тысячи людей, и нужно, чтобы обновления разбирали несколько копий бота. Или хостинг, на котором можно запускать только веб-приложения.

Что понадобится. Доменное имя для сервера, сертификат HTTPS и веб-сервер внутри бота. Вебхук и опрос вместе не работают: по FAQ Telegram, пока вебхук установлен, получать обновления опросом нельзя. Это тот же принцип, что в уроке 9.2: у токена один способ получать обновления.

Для ПривычкаБота опрос подходит отлично: пользователей немного, сервер один. Вебхуки не делают бота быстрее для десятка людей.

Первый шаг. В aiogram для вебхуков есть готовая связка с aiohttp-сервером — той же библиотекой, что в модуле 8, только в роли сервера, а не клиента.

🐳 8. Docker

Что это. Способ упаковать бота вместе с Python, библиотеками и настройками в один образ, который запускается одинаково на любом сервере.

Сигнал. На сервере уже три бота, у каждого свой Python и свои библиотеки. Или переезд на новый сервер по уроку 9.2 стал рутиной на час, и хочется, чтобы он занимал одну команду.

Посмотрите на урок 9.2 с этой стороны: вы руками ставили python3.12-venv, создавали окружение, ставили библиотеки по requirements.txt, запускали. Dockerfile — это урок 9.2, записанный в файл: по нему Docker повторит всё сам. А systemd из урока 9.3 по-прежнему будет следить, чтобы контейнер работал.

Первый шаг. Установить Docker на свой компьютер и собрать образ для ПривычкаБота: базовый образ Python 3.12, копирование проекта, pip install -r requirements.txt, запуск bot.py.

⭐ 9. Платежи

Что это. Оплата прямо в чате: бот присылает счёт, пользователь платит, не выходя из Telegram.

Сигнал. Бот приносит людям пользу, и они готовы за неё платить: например, за расширенную статистику или больше привычек.

Как это устроено

Для цифровых товаров и услуг, а функции бота — именно такие, Telegram требует оплату в своей валюте — звёздах (Telegram Stars). В документации Telegram для них код валюты XTR; другие валюты и сторонние платёжные системы для цифровых товаров не допускаются. Порядок такой:

  1. Бот отправляет счёт методом sendInvoice с валютой XTR.
  2. Пользователь нажимает «Оплатить», и боту приходит обновление pre_checkout_query. На него нужно ответить в течение 10 секунд, иначе оплата отменится.
  3. После оплаты приходит сообщение с successful_payment. Только после него можно открывать доступ: ответ на pre_checkout_query оплатой ещё не является.
  4. Идентификатор платежа из successful_payment нужно сохранить: по нему делается возврат.

Каждый шаг вам знаком по форме: новый тип обновления — новый хэндлер (модуль 4), ответ за ограниченное время — как callback.answer() (урок 5.1), запись в базу перед выдачей — как mark_sent() (9.1).

⚠️ Не только код:
Приём денег — это ещё и правила Telegram для продавцов, и налоги в вашей стране. Перед тем как брать оплату, прочитайте условия Telegram и разберитесь с юридической стороной — здесь курс не советчик.

Первый шаг. Страница документации Telegram «Bot Payments API for Digital Goods and Services» — ссылка в итоге урока. Счёт на 1 звезду в тестовом боте, чтобы пройти весь путь до successful_payment.

Для каждого сигнала спросите: что именно не справляется — проверка, память процесса, файл базы, ручная установка или поток сообщений?

🌱 10. Что доработать в ПривычкаБоте

Новые технологии не обязательны, чтобы бот рос. Вот доработки, для которых хватит того, что вы уже знаете. Каждая — хорошее самостоятельное задание: сначала решить, как это должно выглядеть для пользователя, потом — где в коде это живёт.

Доработка Что понадобится из курса
Удалить или переименовать привычку Кнопки (модуль 5), короткий диалог (модуль 6), DELETE и UPDATE; отметки удалённой привычки тоже удалить (модуль 7)
Учитывать частоту: «3 раза в неделю» выполнено — привычка не напоминает до понедельника Подсчёт отметок за неделю (7.3), send_due() (9.1)

Часовой пояс пользователя Геокодер уже присылает timezone (8.2), zoneinfo (9.1)

После каждой доработки — тест на новую функцию, если она без message, обновление сервера по уроку 9.3 и приёмка затронутых пунктов по уроку 9.5. Этот цикл — «сделать, проверить, выкатить, принять» — и есть работа над ботом в проде.

Между этими точками было много технологий, но учились вы не им. Это и есть инженерный подход, с которого начинался урок 1.1. С ним можно браться за следующий бот, каким бы он ни был.
