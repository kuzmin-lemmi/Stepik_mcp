Урок 9.4. Бот, который не падает: обработчик ошибок и логи

Аннотация:
После урока 9.3 ПривычкаБот — служба сервера: systemd поднимет его после сбоя и после перезагрузки. Но systemd видит бота только снаружи: жив процесс или нет. А бот может быть жив и при этом сломан изнутри.

Сегодня устроим боту аварию и увидим две такие поломки. Хэндлер падает — пользователь остаётся без ответа. Цикл напоминаний падает — и умирает молча, хотя бот продолжает отвечать на команды. Починим обе и настроим журнал так, чтобы по нему было видно, что случилось, когда и с кем.

🛠 Как устроен урок:
Опыты — на вашем компьютере, с ботом, запущенным из терминала. Меняем ПривычкаБот: новый файл handlers/errors.py, правки в bot.py, reminders.py и texts.py. В разделе 7 обновлённый бот переедет на сервер способом из урока 9.3.
🎯 Цель урока:
• Устроить аварию и увидеть, что получает пользователь, — раздел 1
• Найти задачу, которая умерла молча, — раздел 2
• Настроить журнал: время, уровень, источник — раздел 3
• Написать обработчик ошибок aiogram — разделы 4–5
• Застраховать цикл напоминаний — раздел 6
• Искать ошибки в журнале на сервере — раздел 7

💥 1. Авария: база занята

Нужна поломка, которая не зависит от нашего кода и может случиться на любом сервере. Вот такая: базу habits.db открыла другая программа и держит её. Например, вы зашли на сервер, открыли базу, чтобы посмотреть или поправить данные, и начали изменение, но не закончили его. Пока изменение не закончено, SQLite не пускает в базу других. aiosqlite подождёт 5 секунд и сдастся с ошибкой database is locked.

Изобразим такую программу. Создайте в папке bg_lab из урока 9.1 файл lock.py:

"""Держит habits.db заблокированной на запись N секунд — как открытая в другой программе база."""
import sqlite3, sys, time
db = sqlite3.connect(sys.argv[1], isolation_level=None)
db.execute("BEGIN EXCLUSIVE")
time.sleep(float(sys.argv[2]))
db.execute("ROLLBACK")

Программа открывает базу, начинает изменение командой BEGIN EXCLUSIVE — «никого не пускать», держит её указанное число секунд и отменяет изменение. Данные она не меняет.

Опыт

Запустите бота из терминала, как раньше: python bot.py. Во втором терминале, в папке проекта, займите базу на 9 секунд:

python ../bg_lab/lock.py habits.db 9

Аня не получила ничего. Ни ответа, ни сообщения об ошибке — бот промолчал. Для неё это выглядит так, будто бот сломался или не услышал. А в терминале бота:

Это пишет aiogram: Cause exception while process update — «исключение при обработке обновления». Ниже — traceback: ошибка вылетела из get_habits() внутри cmd_today. Без времени: когда это случилось, мы не знаем. Без пользователя: у кого не сработал /today, тоже не знаем. На сервере эти строки лягут в журнал, и через неделю из них не понять, что произошло.

🕳 2. Задача, которая умерла молча

В опыте мы занимали базу на стыке минут: с 19:56:57 до 19:57:06. Ровно в 19:57:00 проснулся цикл напоминаний из урока 9.1 и вызвал send_due(). Та пошла в базу за привычками — и тоже получила database is locked.

У Бориса привычка «Бег» с напоминанием на 19:58. Мы подождали до 19:58:10. Напоминание не пришло. В терминале бота — ни одной новой строки. Бот при этом отвечал на /today как ни в чём не бывало.

Что случилось, мы узнали только тогда, когда остановили бота Ctrl+C. В самом конце вывода:

future: <Task finished name='Task-2' coro=<reminder_loop() done, defined at .../habit_bot/reminders.py:69> exception=OperationalError('database is locked')>
Traceback (most recent call last):
  File "reminders.py", line 71, in reminder_loop
    await send_due(bot, clock.now())
  File "reminders.py", line 51, in send_due
    for habit in await database.get_all_habits():
  File "database.py", line 217, in get_all_habits
    cursor = await db.execute(
  ...
sqlite3.OperationalError: database is locked

Task exception was never retrieved — «исключение задачи так никто и не забрал». Задача reminder_loop() завершилась ещё в 19:57: исключение вылетело из send_due(), прошло через while True, и цикл закончился. Задача умерла.

Почему никто не заметил

Вспомните модуль 3: исключение внутри задачи хранится в самой задаче, пока кто-нибудь не дождётся её через await. Тогда оно вылетит в том месте. Но цикл напоминаний мы запустили через create_task() именно для того, чтобы его не ждать. Исключение легло в задачу и лежало там, пока программа не завершилась. Только тогда asyncio сообщил: была ошибка, и её никто не посмотрел.

И systemd из урока 9.3 здесь не поможет. Процесс жив, Telegram опрашивается, на команды бот отвечает. Перезапускать нечего. Напоминания перестали приходить — навсегда, до следующего перезапуска бота. Это самая опасная поломка модуля: бот выглядит здоровым.

🔑 Ошибка в фоновой задаче убивает задачу, а не бота:
Исключение, вылетевшее из корутины, запущенной через create_task(), тихо завершает её. Бот продолжает работать, а об ошибке видно только при остановке программы.

🧪 Задание

Вопрос: Почему смерть цикла напоминаний не видна ни в терминале, ни в systemctl status?

  1. Исключение остаётся внутри задачи, которую никто не ждёт через await, а процесс бота продолжает работать ✅
  2. aiogram перехватывает все исключения и скрывает их
  3. systemd перезапускает задачу, и ошибка теряется
  4. database is locked — не исключение, а предупреждение

Отзыв на верный ответ:
Верно. asyncio сообщает об ошибке такой задачи только при её уничтожении, обычно — при остановке программы. А systemd следит за процессом, не за задачами внутри него.

Подсказка при неверном ответе:
Когда в опыте появилось сообщение Task exception was never retrieved? И что видит systemd: процесс или отдельные корутины внутри него?

📒 3. Журнал со временем и уровнями

Прежде чем чинить, научимся видеть. В уроке 1.2 мы знакомились с модулем logging: уровни, basicConfig(), логгер на каждый модуль. Логгеры в ПривычкаБоте уже есть — logging.getLogger(__name__) в weather.py и reminders.py. Но журнал никто не настроил, и Python печатает только предупреждения и ошибки, без времени и уровня (урок 8.4).

Настроим. В bot.py добавьте импорт:

import asyncio
import logging

from aiogram import Bot, Dispatcher

И строку формата перед main(), а настройку — первой строкой внутри:

LOG_FORMAT = "%(asctime)s %(levelname)s %(name)s: %(message)s"

async def main() -> None:
    logging.basicConfig(level=logging.INFO, format=LOG_FORMAT)
    await database.init_db()

Формат читается так:

%(asctime)s      →  дата и время с миллисекундами
%(levelname)s    →  уровень: INFO, WARNING, ERROR
%(name)s         →  чей логгер: имя модуля, где создан getLogger(__name__)
%(message)s      →  сам текст

level=logging.INFO — печатать всё от INFO и серьёзнее. Почему настройка внутри main(), а не в начале файла? Так она выполняется только при запуске бота. Если bot.py кто-то импортирует, например проверочный скрипт, его журнал наша настройка не тронет.

Запустите бота и отправьте /today:

ПривычкаБот запущен. Ctrl+C для остановки.
2026-11-01 16:58:37,801 INFO aiogram.dispatcher: Start polling
2026-11-01 16:58:37,805 INFO aiogram.dispatcher: Run polling for bot @habit_demo_bot id=123456789 - 'ПривычкаБот'
2026-11-01 16:58:38,425 INFO aiogram.event: Update id=13 is handled. Duration 11 ms by bot id=123456789

Заговорил aiogram. Эти строки он писал и раньше, но без настройки уровень INFO не печатался. Start polling — опрос начался. Update id=13 is handled. Duration 11 ms — обновление обработано за 11 миллисекунд: по такой строке на каждое сообщение и нажатие. Имя после уровня показывает, кто пишет: aiogram.dispatcher, aiogram.event. Записи наших модулей будут подписаны weather, reminders.

Время в журнале — время компьютера, на котором работает бот. На сервере это UTC. clock.py из урока 9.1 отвечает за расписание бота, а журналу нужно время машины: по нему его сверяют с журналами системы.

Какой уровень для чего

Уровень Когда Пример в ПривычкаБоте
DEBUG подробности для отладки, обычно выключены —
INFO обычное событие, всё идёт как надо «Город не найден» в weather.py, запуск опроса

Вопрос, который задают себе каждый раз: нужно ли человеку что-то сделать? Город не нашёлся — нет, бот уже ответил. Сервис погоды не ответил — пока нет, но если такое каждый день, стоит разобраться. Упал хэндлер — да.

🛟 4. Обработчик ошибок

Теперь первая поломка: хэндлер упал, и пользователь не получил ответа. Чинить каждый хэндлер по отдельности — обернуть все обращения к базе в try — долго, и какой-нибудь всё равно забудется. Нужно одно место, куда попадают ошибки из всех хэндлеров.

Такое место в aiogram есть. Когда хэндлер падает, aiogram не сразу пишет Cause exception, а сначала ищет обработчик ошибок — функцию, зарегистрированную через @router.errors(). Нашёл — передаёт ошибку ему. Не нашёл — пишет то, что мы видели в разделе 1.

Шаг 1. Текст для пользователя

Добавьте в конец texts.py:

ERROR = "Что-то пошло не так. Попробуйте ещё раз через минуту."

Текст честный: что-то сломалось не по вине пользователя, и стоит попробовать позже. Подробностей вроде database is locked пользователю не нужно: ему они ничего не скажут.

Шаг 2. Роутер ошибок

Создайте файл handlers/errors.py:

"""Ошибка в любом хэндлере: ответ пользователю и подробная запись в журнал."""
import logging

from aiogram import Router
from aiogram.exceptions import TelegramAPIError
from aiogram.types import ErrorEvent

import texts

router = Router(name="errors")
logger = logging.getLogger(__name__)

@router.errors()
async def on_error(event: ErrorEvent) -> None:
    update = event.update
    if update.message is not None:
        user_id = update.message.from_user.id
        what = update.message.text
    elif update.callback_query is not None:
        user_id = update.callback_query.from_user.id
        what = update.callback_query.data
    else:
        user_id = None
        what = None

    logger.error(
        "Ошибка в хэндлере: пользователь %s, событие %r",
        user_id,
        what,
        exc_info=event.exception,
    )

    try:
        if update.message is not None:
            await update.message.answer(texts.ERROR)
        elif update.callback_query is not None:
            await update.callback_query.answer(texts.ERROR, show_alert=True)
    except TelegramAPIError:
        logger.warning("Не удалось сообщить пользователю %s об ошибке", user_id)

Разберём по частям.

ErrorEvent

Обработчик получает не сообщение, а событие ошибки ErrorEvent. В нём две вещи: event.exception — само исключение, и event.update — обновление от Telegram, на котором хэндлер упал. В обновлении есть либо сообщение (update.message), либо нажатие (update.callback_query), — второе будет None.

Запись в журнал

Первым делом — записать, что случилось. Номер пользователя и что он прислал: текст сообщения или callback_data кнопки. Этого не хватало в разделе 1. %r печатает значение в кавычках, как !r в f-строке (урок 8.3): видно, что '/today' — строка. Не f-строка, а %s и аргументы — как в weather.py: так принято в logging.

exc_info=event.exception добавляет к записи traceback этого исключения. Без него в журнале будет только наша строка, а где именно упало — не узнать.

Ответ пользователю

Потом — ответить. На сообщение отвечаем сообщением. На нажатие — окном show_alert: под кнопкой нельзя прислать сообщение-ответ, а окно пользователь увидит точно.

Почему ответ завернут в try? Ошибка в хэндлере могла случиться потому, что не работает сам Telegram. Тогда и ответ не уйдёт, и обработчик упадёт внутри себя. Ловим TelegramAPIError — общего предка ошибок Telegram в aiogram, как aiohttp.ClientError в уроке 8.3, — и записываем, что сообщить не удалось.

Шаг 3. Подключить

В bot.py добавьте errors в импорт роутеров:

from handlers import add, common, errors, fallback, guard, habits

И подключите его первым:

    dp.include_router(errors.router)
    dp.include_router(guard.router)

Порядок guard → common → habits → add → fallback из модуля 6 не меняется. В роутере errors нет ни одного хэндлера сообщений, поэтому он никого не перехватит, а ошибки получает от всех.

🔁 6. Страховка цикла напоминаний

Вторая поломка: исключение в send_due() убивает цикл. Обработчик ошибок aiogram здесь не поможет: он ловит ошибки хэндлеров, а цикл напоминаний — не хэндлер, его запустили мы сами.

Цикл должен пережить любую ошибку в одной проверке и попробовать снова через минуту. Замените reminder_loop() в reminders.py:

async def reminder_loop(bot: Bot) -> None:
    while True:
        try:
            await send_due(bot, clock.now())
        except Exception:
            logger.exception("Сбой в цикле напоминаний, повтор через минуту")
        await asyncio.sleep(60 - clock.now().second)

Почему здесь except Exception

В уроке 8.3 мы ловили только ожидаемые ошибки сети, а except Exception: pass назвали опасным: он прячет ошибки нашего кода. Здесь же стоит except Exception. Противоречия нет — правило урока 2.6 звучало так: except Exception допустим как страховка, но только с обязательным логированием.

Это ровно такой случай. Какие ошибки случатся в send_due(), мы заранее не знаем: занятая база, сбой Telegram, ошибка в нашем коде. Знаем одно: из-за любой из них цикл не должен остановиться навсегда. А чтобы ничего не спряталось, ошибка записывается.

logger.exception() — это logger.error(), который сам добавляет traceback текущего исключения. Работает только внутри except. В обработчике aiogram мы передавали исключение через exc_info: там его ловили не мы.

Что except Exception не поймает — тоже по уроку 2.6: KeyboardInterrupt и asyncio.CancelledError. Они не наследуются от Exception. Поэтому Ctrl+C и systemctl stop по-прежнему останавливают бота, а не превращаются в «сбой, повтор через минуту». Голый except: поймал бы и их.

Вопрос: В reminder_loop() вместо except Exception: с logger.exception() написали голый except: с pass. Чем это плохо?

Вспомните урок 2.6: что ловит голый except:, кроме обычных ошибок? И как вы узнаете о сбое, если в except только pass?

"""Напоминания: бот сам пишет пользователям по расписанию."""
import asyncio
import logging
from datetime import datetime, timedelta

from aiogram import Bot, html
from aiogram.exceptions import TelegramForbiddenError
from aiogram.types import InlineKeyboardMarkup

import clock
import database
import keyboards
import texts
from handlers.habits import build_morning_text

MORNING_TIME = "07:30"
CATCH_UP = timedelta(minutes=15)

logger = logging.getLogger(__name__)


def is_due(remind_time: str, now: datetime) -> bool:
    hours, minutes = remind_time.split(":")
    planned = now.replace(
        hour=int(hours), minute=int(minutes), second=0, microsecond=0
    )
    return planned <= now < planned + CATCH_UP


async def deliver(
    bot: Bot,
    user_id: int,
    text: str,
    markup: InlineKeyboardMarkup | None = None,
) -> None:
    try:
        await bot.send_message(user_id, text, reply_markup=markup)
    except TelegramForbiddenError:
        logger.warning("Пользователь %s заблокировал бота", user_id)


async def send_due(bot: Bot, now: datetime) -> None:
    day = now.date()

    if is_due(MORNING_TIME, now):
        for user_id in await database.get_user_ids():
            if await database.mark_sent(user_id, "morning", day):
                text = await build_morning_text(user_id, day)
                await deliver(bot, user_id, text)

    for habit in await database.get_all_habits():
        if not is_due(habit["remind_time"], now):
            continue

        user_id = habit["user_id"]
        done_ids = await database.get_done_ids(user_id, day)
        if habit["id"] in done_ids:
            continue

        if await database.mark_sent(user_id, f"habit_{habit['id']}", day):
            await deliver(
                bot,
                user_id,
                texts.REMINDER.format(name=html.quote(habit["name"])),
                keyboards.reminder_keyboard(habit["id"], habit["name"]),
            )


async def reminder_loop(bot: Bot) -> None:
    while True:
        try:
            await send_due(bot, clock.now())
        except Exception:
            logger.exception("Сбой в цикле напоминаний, повтор через минуту")
        await asyncio.sleep(60 - clock.now().second)
