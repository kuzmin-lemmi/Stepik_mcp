Урок 8.3. Таймауты и падения API: бот не должен зависать

Аннотация:
В уроке 8.2 ПривычкаБот научился разбирать ответ Open-Meteo и переживать ответ не того формата. Но всё это работает, только когда ответ пришёл. Сегодня разберём случаи хуже: сервис думает слишком долго, сети нет, вместо данных пришла ошибка или веб-страница.

Цель — одна функция get_weather(city). Она либо возвращает погоду, либо None, но никогда не роняет бота и не заставляет пользователя ждать минутами.

🛠 Как устроен урок:
Работаем в папке http_lab из уроков 8.1 и 8.2, рядом с weather_parse.py. Новый файл — weather_net.py с запросами к сервису. В практикуме 8.4 оба файла станут одним weather.py в проекте. Файлы ПривычкаБота сегодня не меняются.
🎯 Цель урока:
• Понять, чем опасен медленный сервис, — раздел 1
• Ограничить ожидание через ClientTimeout — раздел 2
• Получить каждый вид отказа своими руками — раздел 3
• Написать get_weather(), которая ловит только нужные исключения, — раздел 4
• Показать пользователю заглушку вместо молчания — раздел 5
• Понять, почему не стоит повторять запрос в цикле, — раздел 6
• Проверить все ветки, не поднимая своего сервера, — раздел 7

🐢 1. Сервис отвечает тридцать секунд

В уроке 8.1 Open-Meteo отвечал за доли секунды. Так бывает почти всегда. Но однажды сервис перегружен и отвечает через тридцать секунд. Или не отвечает вовсе: запрос ушёл, а ответа нет.

Что в это время происходит с ботом? Event loop не стоит: запрос через aiohttp отдаёт управление, это мы проверили в уроке 8.1. Борис нажимает кнопки, бот ему отвечает.

А вот хэндлер, который пошёл за погодой, висит. Аня отправила команду и смотрит в пустой чат. Она не знает, что бот ждёт чужой сервис. Для неё бот сломался.

Сколько она будет ждать? Если ничего не настраивать, столько, сколько разрешает aiohttp. Проверим в терминале с окружением проекта:

python -c "import aiohttp; print(aiohttp.client.DEFAULT_TIMEOUT)"
ClientTimeout(total=300, connect=None, sock_read=None, sock_connect=30, ceil_threshold=5)

total=300 — общее время на запрос по умолчанию: 300 секунд, пять минут. Пять минут без ответа — это уже не «бот думает», а «бот умер». Пользователь закроет чат раньше.

Ждать дольше нескольких секунд погоду, которая нужна для одной строки в утреннем сообщении, бессмысленно. Значит, предел нужно поставить самим.

🔑 Не зависание бота, а зависание хэндлера:
Медленный сервис не останавливает event loop, но держит хэндлер, который его ждёт. Пользователь, который спросил, остаётся без ответа. По умолчанию aiohttp ждёт до пяти минут.

⏱ 2. Таймаут: ClientTimeout

Предел ожидания задаёт объект aiohttp.ClientTimeout. Аргумент total — сколько секунд разрешено на весь запрос: соединиться, отправить, получить ответ.

Чтобы увидеть, как срабатывает таймаут, сервис должен не успеть. Ждать, пока Open-Meteo начнёт тормозить, мы не будем — сделаем предел меньше, чем нужно любому сервису: одна тысячная секунды. Создайте в http_lab файл timeout_demo.py:

import asyncio
import time

import aiohttp

URL = "https://api.open-meteo.com/v1/forecast"
PARAMS = {
    "latitude": 55.79,
    "longitude": 49.12,
    "current": "temperature_2m,weather_code",
}
TIMEOUT = aiohttp.ClientTimeout(total=0.001)


async def main() -> None:
    start = time.monotonic()
    try:
        async with aiohttp.ClientSession(timeout=TIMEOUT) as session:
            async with session.get(URL, params=PARAMS) as response:
                data = await response.json()
        print(data["current"])
    except TimeoutError:
        print("Не дождались ответа")
    print(f"прошло: {time.monotonic() - start:.3f} с")


asyncio.run(main())

Таймаут передаётся при создании сессии: ClientSession(timeout=TIMEOUT). Он действует на каждый запрос этой сессии. Превышение предела — исключение TimeoutError, его и ловим.

Запустите python timeout_demo.py:

Не дождались ответа
прошло: 0.002 с

Ответ не успел за тысячную долю секунды, и программа не стала ждать: исключение, сообщение, выход. Теперь замените строку с таймаутом на разумную:

TIMEOUT = aiohttp.ClientTimeout(total=5)

И запустите ещё раз:

{'time': '2026-11-01T14:15', 'interval': 900, 'temperature_2m': 3.1, 'weather_code': 0}
прошло: 0.054 с

Ответ уложился в пять секунд — таймаут ничего не заметил. Предел мешает только тогда, когда сервис не успевает.

Вы это уже видели

В уроке 3.4 похожий предел ставила asyncio.wait_for():

урок 3.4:  await asyncio.wait_for(slow_operation(), timeout=2)
урок 8.3:  aiohttp.ClientSession(timeout=aiohttp.ClientTimeout(total=5))

Принцип тот же: ждём не дольше предела, не успели — TimeoutError. И исключение то же самое, встроенное. Разница в том, что aiohttp встроила таймаут в себя: оборачивать каждый запрос в wait_for() не нужно.

В уроке 3.4 было обещание: «в модуле про внешние API таймаут станет обязательной частью каждого запроса». Этот модуль наступил.

💡 Таймаут для одного запроса:
session.get() тоже принимает timeout=, и тогда предел действует только на этот запрос. Нам удобнее общий: все запросы к погоде ждём одинаково.
🔑 Ждём не дольше, чем решили сами:
ClientTimeout(total=5), переданный в ClientSession(timeout=...), ограничивает каждый запрос пятью секундами. Не успел — TimeoutError.

🧪 Задание

Вопрос: Нужно, чтобы каждый запрос сессии ждал ответа не дольше 5 секунд. Какая запись это делает?

  1. aiohttp.ClientSession(timeout=aiohttp.ClientTimeout(total=5)) ✅
  2. aiohttp.ClientSession(timeout=aiohttp.ClientTimeout(total=5000))
  3. await response.json(timeout=5)
  4. asyncio.run(main(), timeout=5)

Отзыв на верный ответ:
Верно. Предел задаётся в секундах и передаётся при создании сессии. Для одного запроса его можно передать и в session.get(..., timeout=...).

Подсказка при неверном ответе:
Посмотрите на timeout_demo.py: в какую строку передан TIMEOUT? В каких единицах записано total=0.001 — секундах или миллисекундах?

🗂 3. Каталог отказов

Таймаут — не единственное, что может случиться с запросом. Соберём все отказы, которые встретятся боту, и каждый получим запуском. Нужна одна программа, которой можно сказать, какой отказ устроить.

Создайте fail_demo.py:

import asyncio
import sys

import aiohttp

FORECAST_URL = "https://api.open-meteo.com/v1/forecast"
PARAMS = {
    "latitude": 55.79,
    "longitude": 49.12,
    "current": "temperature_2m,weather_code",
}
BAD_PARAMS = {"latitude": 55.79, "longitude": 49.12, "current": "temperatura"}
CASES = {
    "slow": (FORECAST_URL, PARAMS, 0.001),
    "offline": ("https://api.open-meteo.invalid/v1/forecast", PARAMS, 5),
    "html": ("https://open-meteo.com/", {}, 5),
    "404": ("https://api.open-meteo.com/v1/forecat", PARAMS, 5),
    "400": (FORECAST_URL, BAD_PARAMS, 5),
}


async def main(case: str) -> None:
    url, params, seconds = CASES[case]
    timeout = aiohttp.ClientTimeout(total=seconds)
    async with aiohttp.ClientSession(timeout=timeout) as session:
        async with session.get(url, params=params) as response:
            print("статус:", response.status)
            data = await response.json()
    print(data)


asyncio.run(main(sys.argv[1]))

В словаре CASES пять сценариев: адрес, параметры и таймаут для каждого. Какой запустить, программа узнаёт из командной строки: sys.argv[1] — первое слово после имени файла. try здесь нарочно нет: хотим увидеть исключения как есть.

Traceback у сетевых ошибок длинный: большая часть строк — внутренности asyncio и aiohttp. Как в уроке 1.2, читаем его снизу вверх: последняя строка говорит, что случилось, строка с fail_demo.py выше — где. Ниже мы оставили только их.

Отказ 1. Сервис не успел

Таймаут в тысячную секунды, как в разделе 2. Запустите python fail_demo.py slow:

Знакомый TimeoutError. Обратите внимание: у него нет текста после имени. Это пригодится в разделе 4.

Отказ 2. Сервер не найден

Адрес api.open-meteo.invalid не существует: домен .invalid зарезервирован как заведомо несуществующий. Для программы это то же самое, что выключенный Wi-Fi: найти сервер не удалось. Запустите python fail_demo.py offline:

Traceback (most recent call last):
  File "fail_demo.py", line 32, in <module>
    asyncio.run(main(sys.argv[1]))
  ...
  File "fail_demo.py", line 26, in main
    async with session.get(url, params=params) as response:
  ...
aiohttp.client_exceptions.ClientConnectorDNSError: Cannot connect to host api.open-meteo.invalid:443 ssl:default [Name or service not known]

ClientConnectorDNSError — «не удалось соединиться: имя хоста не нашлось». До запроса дело не дошло. Если вместо имени нет сети вовсе, или сервер не принимает соединения, исключение будет родственным: ClientConnectorError. Его потомок ClientConnectorDNSError мы только что видели.

Отказ 3. Пришёл не JSON

Адрес https://open-meteo.com/ — главная страница сайта, а не API. Сервер ответит, но веб-страницей для людей. Так бывает и с настоящими API: при перегрузке вместо данных отдают страницу «сервис временно недоступен». Запустите python fail_demo.py html:

  File "fail_demo.py", line 32, in <module>
    asyncio.run(main(sys.argv[1]))
  ...
  File "fail_demo.py", line 28, in main
    data = await response.json()
           ^^^^^^^^^^^^^^^^^^^^^
  ...
aiohttp.client_exceptions.ContentTypeError: 200, message='Attempt to decode JSON with unexpected mimetype: text/html; charset=utf-8', url='https://open-meteo.com/'

Статус 200 — сервер считает, что всё хорошо. Но response.json() посмотрел на тип ответа: text/html, а не JSON. И отказался разбирать: ContentTypeError.

Отказ 4. Город не найден

Этот отказ вы уже знаете из урока 8.2: геокодер отвечает статусом 200, но без ключа "results". Исключения здесь нет — это обычный ответ, и его разбирает parse_city(), возвращая None.

🔑 Каждый отказ — своё исключение:
Не успел — TimeoutError. Не нашёл сервер — ClientConnectorError. Пришла страница вместо JSON — ContentTypeError. Город не найден — не исключение, а ответ без "results".

🚦 3. Каталог отказов: ошибки сервера

Осталось два сценария в CASES: опечатка в адресе (forecat вместо forecast) и неверный параметр, как в уроке 8.1. Запустите python fail_demo.py 404:

статус: 404
{'reason': 'Not Found', 'error': True}

И python fail_demo.py 400:

статус: 400
{'error': True, 'reason': 'Invalid value: Cannot initialize SurfacePressureAndHeightVariable<VariableAndPreviousDay, VariableOrSpread<ForecastPressureVariable>, ForecastHeightVariable> from invalid String value temperatura'}

Исключений нет. Программа отработала до конца и напечатала словарь. Статусы — 404 и 400, «не найдено» и «ошибка в запросе», но aiohttp на статус не смотрит: какой ответ пришёл, такой и отдаёт. Open-Meteo присылает ошибки в формате JSON, поэтому json() разобрал их без возражений.

Чем это опасно? Представьте эту ошибку в боте. describe_weather() не найдёт в ответе "current" и вернёт None. В логе это выглядит как «сервис изменил формат», хотя на деле мы ошиблись в адресе. Для геокодера хуже: parse_city() не найдёт "results", и бот скажет Ане «город не найден» про её Казань.

raise_for_status()

Нужно, чтобы ответ с ошибкой оставался ошибкой. Для этого у ответа есть метод raise_for_status(): статус 400 и выше — исключение, иначе ничего. Добавьте в fail_demo.py строку сразу после печати статуса:

            print("статус:", response.status)
            response.raise_for_status()

Запустите python fail_demo.py 404 ещё раз:

  File "fail_demo.py", line 33, in <module>
    asyncio.run(main(sys.argv[1]))
  ...
  File "fail_demo.py", line 28, in main
    response.raise_for_status()
  ...
aiohttp.client_exceptions.ClientResponseError: 404, message='Not Found', url='https://api.open-meteo.com/v1/forecat?latitude=55.79&longitude=49.12&current=temperature_2m,weather_code'

И python fail_demo.py 400:

статус: 400
Traceback (most recent call last):
  File "fail_demo.py", line 33, in <module>
    asyncio.run(main(sys.argv[1]))
  ...
  File "fail_demo.py", line 28, in main
    response.raise_for_status()
  ...

Теперь каждый ответ с ошибкой — исключение ClientResponseError. В нём код статуса, его название и адрес. Так же поведёт себя и ответ 500 «сервер сломался»: на ошибку сервера Open-Meteo вызвать нарочно нельзя, но для raise_for_status() 500 ничем не отличается от 404 — оба 400 и выше.

Кто кому родственник

Отказов пять, исключений четыре. Ловить их по одному было бы долго. Но у трёх из них общий предок: aiohttp.ClientError. Проверим через issubclass() — «является ли этот класс потомком того». Создайте hierarchy_demo.py:

import aiohttp

errors = [
    aiohttp.ClientConnectorError,
    aiohttp.ClientResponseError,
    aiohttp.ContentTypeError,
    TimeoutError,
]
for error in errors:
    print(error.__name__, issubclass(error, aiohttp.ClientError))
ClientConnectorError True
ClientResponseError True
ContentTypeError True
TimeoutError False
aiohttp.ClientError
├── ClientConnectorError        сервер не найден, соединения нет
└── ClientResponseError         ответ со статусом 400 и выше
    └── ContentTypeError        пришёл не JSON

TimeoutError                    не успел — встроенное, отдельно

Значит, все отказы покрывают два типа: aiohttp.ClientError и TimeoutError. Это и понадобится в разделе 4.

🔑 Ошибка сервера — не данные:
Без raise_for_status() ответ 404 или 400 разбирается как обычный JSON и дальше выглядит как «формат не тот» или «города нет». С ним он становится ClientResponseError.

🧰 4. get_weather(): одна функция на все отказы

Каталог собран. Теперь напишем функцию, которую будет вызывать бот. Правило из урока 2.6: ловим только то, что ожидаем и умеем обработать. Голый except: запрещён, а пользователю — понятный ответ, себе — запись в лог.

Ожидаем мы ровно каталог из раздела 3. Обработать умеем одним способом: погоды не будет, вернём None.

Шаг 1. weather_net.py

Создайте в http_lab файл weather_net.py:

"""Запросы к Open-Meteo."""
import logging

import aiohttp

from weather_parse import describe_weather, parse_city

GEO_URL = "https://geocoding-api.open-meteo.com/v1/search"
FORECAST_URL = "https://api.open-meteo.com/v1/forecast"
TIMEOUT = aiohttp.ClientTimeout(total=5)

logger = logging.getLogger(__name__)


async def get_json(url: str, params: dict) -> dict:
    async with aiohttp.ClientSession(timeout=TIMEOUT) as session:
        async with session.get(url, params=params) as response:
            response.raise_for_status()
            return await response.json()


async def get_weather(city: str) -> str | None:
    try:
        geo_params = {"name": city, "count": 1, "language": "ru"}
        geo = await get_json(GEO_URL, geo_params)
        coords = parse_city(geo)
        if coords is None:
            logger.info("Город не найден: %s", city)
            return None

        latitude, longitude = coords
        params = {
            "latitude": latitude,
            "longitude": longitude,
            "current": "temperature_2m,weather_code",
        }
        forecast = await get_json(FORECAST_URL, params)
    except (aiohttp.ClientError, TimeoutError) as error:
        name = type(error).__name__
        logger.warning("Погода для %s недоступна: %s", city, name)
        return None

    weather = describe_weather(forecast)
    if weather is None:
        logger.warning("Неожиданный ответ прогноза для %s", city)
    return weather

Разберём по частям.

get_json(): таймаут и статус для каждого запроса

Это функция get_json() из урока 8.2 с двумя добавками: timeout=TIMEOUT у сессии и raise_for_status() у ответа. Обе живут здесь, а не в get_weather(): так любой запрос через get_json() получает их сам, забыть невозможно.

get_weather(): что внутри try

В try — оба запроса: геокодер и прогноз. Любой из них может отказать, и любой отказ ведёт к одному исходу.

except (aiohttp.ClientError, TimeoutError) as error:

Два типа в скобках — кортеж: except ловит любой из них. Это ровно два предка из раздела 3. as error сохраняет пойманное исключение в переменную, чтобы записать в лог, что именно случилось.

Лог: имя исключения

name = type(error).__name__
logger.warning("Погода для %s недоступна: %s", city, name)

В лог пишем имя класса исключения: TimeoutError, ClientResponseError. Почему не текст ошибки? Помните, в разделе 3 у TimeoutError не было текста — в логе осталась бы пустота. Логгер — знакомый с урока 1.2 logging.getLogger(__name__).

Три пути к None

  • Город не найден — parse_city() вернула None. Это не отказ сервиса, в лог — info.
  • Сервис отказал — исключение поймано, в лог — warning с именем исключения.
  • Ответ пришёл, но не того формата, — describe_weather() вернула None, в лог — warning.

Для вызывающего кода все три одинаковы: погоды нет. Различать их нужно нам, а не Ане, — для этого лог.

Шаг 2. Чего ловить нельзя

Соблазн написать короче велик:

    except Exception:
        pass

Проверим, к чему это приводит. Замените на время в weather_net.py строку except (aiohttp.ClientError, TimeoutError) as error: и три строки под ней на эти две. И сделайте опечатку, какую легко сделать в жизни: в строке с прогнозом напишите FORECST_URL вместо FORECAST_URL. Вызовите функцию:

python -c "import asyncio, weather_net; print(asyncio.run(weather_net.get_weather('Казань')))"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  ...
  File "weather_net.py", line 41, in get_weather
    weather = describe_weather(forecast)
                               ^^^^^^^^
UnboundLocalError: cannot access local variable 'forecast' where it is not associated with a value

Ошибка всплыла, но не там и не та. except Exception проглотил NameError от опечатки, pass ничего не записал в лог, а функция пошла дальше. Строкой ниже переменной forecast нет — и вот UnboundLocalError, по которому опечатку не найти. Хуже того: если бы ниже не было обращения к forecast, ошибки не было бы вовсе. Бот бы молча никогда не показывал погоду.

Верните правильный except, опечатку оставьте и вызовите ещё раз:

Traceback (most recent call last):
  File "<string>", line 1, in <module>
  ...
  File "weather_net.py", line 37, in get_weather
    forecast = await get_json(FORECST_URL, params)
                              ^^^^^^^^^^^
NameError: name 'FORECST_URL' is not defined. Did you mean: 'FORECAST_URL'?

Теперь опечатку не поймали: NameError — не сетевая ошибка, её нет в нашем списке. Python показал точное место и даже подсказал правильное имя. Исправьте опечатку.

Так работает правило «ловим только ожидаемое». Отказ сервиса — ожидаем, обрабатываем. Ошибка в нашем коде — не ожидаем, она должна упасть громко, чтобы мы её увидели. Кроме того, except Exception поймал бы и то, что ловить нельзя по уроку 2.6, вроде KeyboardInterrupt или asyncio.CancelledError при остановке бота.

🔑 Отказ сервиса превращается в None, ошибка кода — нет:
except (aiohttp.ClientError, TimeoutError) ловит ровно каталог отказов. Всё остальное — опечатки, ошибки логики — падает с честным traceback.

🧪 Задание

Вопрос: Open-Meteo завис и не отвечает. TIMEOUT в weather_net.py — 5 секунд. Что произойдёт при вызове await get_weather("Казань")?

  1. Примерно через 5 секунд функция вернёт None, а в логе появится WARNING с TimeoutError ✅
  2. Через 5 секунд функция выбросит TimeoutError, и хэндлер упадёт
  3. Функция будет ждать, пока сервис не ответит
  4. Функция сразу вернёт строку "Погоду узнать не удалось."

Отзыв на верный ответ:
Верно. TimeoutError пойман в get_weather() и превращён в None. Какой текст показать пользователю, решает вызывающий код.

Подсказка при неверном ответе:
Найдите в get_weather() строку except. Есть ли среди типов TimeoutError? Что функция делает после записи в лог? А текст для пользователя — есть ли он в weather_net.py?

🧪 Задание

Вопрос: Почему в get_weather() нельзя заменить except (aiohttp.ClientError, TimeoutError) as error: на except Exception: pass?

  1. Он проглотит и ошибки нашего кода, например опечатку, и не оставит записи в логе ✅
  2. except Exception не ловит TimeoutError
  3. pass внутри асинхронной функции запрещён
  4. Так можно, разница только в длине записи

Отзыв на верный ответ:
Верно. Правило урока 2.6: except Exception допустим только как страховка и только с логом. А в get_weather() мы знаем, какие отказы ждём, — их и ловим.

Подсказка при неверном ответе:
Вспомните опыт с FORECST_URL в разделе 4. Какое исключение получилось с except Exception: pass и помогло ли оно найти опечатку?

🪧 5. Заглушка вместо молчания

get_weather() вернула None. Что теперь написать Ане?

Два плохих варианта мы уже отбросили. Упасть — Аня не получит ничего. Промолчать о погоде, будто её и не было, — Аня не поймёт, почему сегодня сообщение другое. Хороший вариант — сказать честно и отправить остальное: привычки на сегодня от погоды не зависят.

Посмотрим, как это выглядит. Создайте morning_demo.py — набросок утреннего сообщения:

import asyncio
import logging

import aiohttp

import weather_net

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

WEATHER_FAILED = "Погоду узнать не удалось."


async def morning_preview(city: str, habits: list[str]) -> str:
    weather = await weather_net.get_weather(city)
    if weather is None:
        weather_line = WEATHER_FAILED
    else:
        weather_line = f"Погода: {weather}."

    lines = ["Доброе утро!", weather_line, "", "Ваши привычки на сегодня:"]
    for name in habits:
        lines.append(f"⬜ {name}")
    return "\n".join(lines)


async def main() -> None:
    habits = ["Зарядка", "Чтение"]
    print(await morning_preview("Казань", habits))
    print()

    weather_net.TIMEOUT = aiohttp.ClientTimeout(total=0.001)
    print(await morning_preview("Казань", habits))


asyncio.run(main())

morning_preview() вызывает get_weather() и выбирает строку: погода или заглушка WEATHER_FAILED. Остальное сообщение собирается одинаково. Во второй раз мы подменили таймаут на тысячную секунды, как в разделе 2, чтобы сервис гарантированно не успел. logging.basicConfig() включает вывод лога в терминал.

Запустите python morning_demo.py:

Доброе утро!
Погода: +3, ясно.

Ваши привычки на сегодня:
⬜ Зарядка
⬜ Чтение

WARNING Погода для Казань недоступна: TimeoutError
Доброе утро!
Погоду узнать не удалось.

Ваши привычки на сегодня:
⬜ Зарядка
⬜ Чтение

Оба сообщения дошли. Во втором вместо погоды — честная фраза, а привычки на месте. В терминале — строка WARNING: Аня её не видит, а мы знаем, что случилось.

Это знакомая форма. В уроке 6.3 неправильный ответ в диалоге не ронял бота: проверка возвращала None, хэндлер отвечал понятной ошибкой, и сценарий продолжался. Отказ сервиса — такая же обычная ветка сценария, как ошибка ввода. Её не надо бояться, её надо предусмотреть.

урок 6.3:  parse_time("вечером")  →  None  →  texts.ERR_TIME
урок 8.3:  get_weather("Казань")  →  None  →  WEATHER_FAILED

В практикуме 8.4 WEATHER_FAILED переедет в texts.py, а набросок станет настоящей функцией утреннего сообщения.

🔑 Отказ сервиса — обычная ветка:
None от get_weather() превращается в заглушку, а остальное сообщение уходит как обычно. Бот не молчит и не падает.

🔁 6. Почему не повторять запрос в цикле

Естественная мысль: не получилось с первого раза — попробуем ещё. Три попытки в цикле, и погода почти всегда найдётся.

Посчитаем, что это даст, когда сервис лежит. Таймаут — 5 секунд. Первая попытка ждёт 5 секунд и падает. Вторая — ещё 5. Третья — ещё 5.

попыток   ждёт Аня, если сервис лежит
   1              5 с
   3             15 с
   5             25 с

Если сервис лёг, он не встанет через пять секунд. Повтор ничего не исправляет — он только растягивает ожидание. Вместо «погоду узнать не удалось» через 5 секунд Аня получит ту же фразу через 15.

Повтор помогает в другом случае: когда отказ случайный — один пакет потерялся, сервер на мгновение был занят. Для таких случаев в серьёзных системах повторяют запрос с растущей паузой и ограниченным числом попыток. Для строки погоды в утреннем сообщении это лишнее: завтра утром бот спросит снова.

🔑 Повтор при недоступном сервисе только удлиняет ожидание:
Одна попытка с разумным таймаутом и честная заглушка лучше трёх попыток, после которых пользователь получит ту же заглушку втрое позже.

🧪 Задание

Вопрос: В get_weather() добавили цикл: при отказе запрос повторяется, всего 3 попытки. Таймаут — 5 секунд. Сервис полностью лежит и не отвечает. Через сколько Аня увидит «Погоду узнать не удалось»?

  1. Примерно через 15 секунд: каждая из трёх попыток ждёт свои 5 секунд ✅
  2. Примерно через 5 секунд: таймаут общий на все попытки
  3. Никогда: цикл будет повторять запрос, пока сервис не ответит
  4. Сразу: после первого отказа повторы не нужны

Отзыв на верный ответ:
Верно. Таймаут действует на каждый запрос отдельно. Три попытки — три ожидания подряд, а результат тот же.

Подсказка при неверном ответе:
Таймаут в ClientSession(timeout=...) ограничивает каждый запрос. Сколько запросов сделает цикл и сколько ждёт каждый?

🧪 7. Проверка всех веток без своего сервера

У get_weather() шесть исходов: погода, город не найден и четыре отказа. Как убедиться, что каждый ведёт себя как задумано? Ждать, пока Open-Meteo сломается, не будем. И поднимать свой сервер, который отвечает ошибками, тоже не нужно.

Каждый отказ из раздела 3 мы устраивали одним значением: адресом или таймаутом. В weather_net.py и адреса, и таймаут — константы модуля. get_json() читает TIMEOUT в момент вызова, get_weather() так же читает FORECAST_URL. Значит, можно подменить константу и вызвать функцию.

Создайте check_demo.py:

import asyncio
import logging

import aiohttp

import weather_net

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")


async def check(title: str, city: str = "Казань") -> None:
    result = await weather_net.get_weather(city)
    print(f"{title}: {result!r}")
    print()


async def main() -> None:
    await check("всё в порядке")
    await check("города нет", "Привычкоград")

    weather_net.TIMEOUT = aiohttp.ClientTimeout(total=0.001)
    await check("сервис не успел")
    weather_net.TIMEOUT = aiohttp.ClientTimeout(total=5)

    weather_net.FORECAST_URL = "https://api.open-meteo.invalid/v1/forecast"
    await check("адреса нет")

    weather_net.FORECAST_URL = "https://api.open-meteo.com/v1/forecat"
    await check("ошибка 404")

    weather_net.FORECAST_URL = "https://open-meteo.com/"
    await check("пришёл не JSON")


asyncio.run(main())

Запись weather_net.TIMEOUT = ... меняет константу внутри модуля weather_net, и следующий вызов увидит новое значение. После проверки таймаута возвращаем пять секунд, иначе дальше не успел бы ни один запрос. !r в f-строке печатает значение в кавычках, как repr(): так строка отличается от None.

Запустите python check_demo.py:

всё в порядке: '+3, ясно'

INFO Город не найден: Привычкоград
города нет: None

WARNING Погода для Казань недоступна: TimeoutError
сервис не успел: None

WARNING Погода для Казань недоступна: ClientConnectorDNSError
адреса нет: None

WARNING Погода для Казань недоступна: ClientResponseError
ошибка 404: None

WARNING Погода для Казань недоступна: ContentTypeError
пришёл не JSON: None

Каждая ветка сработала как задумано:

  • Первый вызов вернул строку погоды.
  • Остальные вернули None, и ни один не уронил программу.
  • Строка в логе разная для каждого случая: по ней видно, что именно случилось.
  • «Города нет» записан как INFO, а отказы сервиса — как WARNING.

Подмена константы в проверке — не обман. Мы не меняли код get_weather(): проверяли ту самую функцию, которую получит бот. Изменилось только то, что приходит снаружи.

🔑 Отказ можно устроить одной константой:
Несуществующий адрес, опечатка в пути, страница вместо API, таймаут в тысячную секунды — каждая ветка проверяется без своего сервера и без ожидания, пока сервис сломается.

📋 Итог урока 8.3

В http_lab рядом с weather_parse.py появился weather_net.py. Его get_weather() возвращает погоду или None, ждёт не дольше пяти секунд и не роняет бота ни при одном отказе сервиса.

  • ✅ Медленный сервис держит хэндлер, а не event loop; по умолчанию aiohttp ждёт 300 секунд
  • ✅ ClientTimeout(total=5) в ClientSession(timeout=...) — предел на каждый запрос; превышение — TimeoutError, как у wait_for()
  • ✅ Отказы: TimeoutError, ClientConnectorError, ClientResponseError, ContentTypeError; город не найден — не исключение
  • ✅ Без raise_for_status() ответ 404 разбирается как данные
  • ✅ except (aiohttp.ClientError, TimeoutError) ловит весь каталог; опечатки в коде падают громко
  • ✅ except Exception: pass прячет баги — правило 2.6
  • ✅ None → заглушка «Погоду узнать не удалось», остальное сообщение уходит как обычно
  • ✅ Повтор при лежащем сервисе только удлиняет ожидание
  • ✅ Ветки проверяются подменой константы: адрес или таймаут
